# KWin Force Blur — размытие рамки окна (декорации)

Цель: заголовок окна Dolphin (рамка Aurorae, `decoration.svg`) должен быть
настоящим матовым стеклом — с реальным гауссовым блюром обоев позади, как у
боковой панели, — а не просто резкой альфа-прозрачностью.

## Откуда взято

Базовый механизм (`source/kwin-forceblur-6.7/`) перенесён из соседнего проекта
`../MacOS/` (`docs/KWIN_FORCEBLUR.md`) — там он собран специально для
Alacritty, у которой нет собственного блюра. Тот же самый бинарник уже стоял
в системе как единственный активный blur-эффект (`blurEnabled=false`,
`forceblurEnabled=true`) и **уже размывал контент Dolphin** (боковую панель) —
это подтверждено штатным механизмом Kvantum
(`KWindowEffects::enableBlurBehind`), не имеет отношения к рамке.

## Почему рамка не размывалась и после переноса форс-класса

Проверено эмпирически, шаг за шагом, на этой же машине:

1. Правка прозрачности в `decoration.svg` (`opacity="0.75"` на заливках
   `decoration-*`/`decoration-inactive-*`, как в `docs/AURORAE_FROSTED_TITLEBAR.md`
   у `../MacOS/`) даёт **резкую** прозрачность — сквозь рамку видны
   необработанные (не размытые) обои, пиксель в пиксель совпадающие с обоями
   вне окна.
2. Живая проверка эталонного WhiteSur на этой же машине (тот же вывод —
   документ `../MacOS/` никогда не проверял именно резкость картинки, только
   совпадение цвета/светлоты) дала **тот же результат**: тоже резкая
   прозрачность, не блюр.
3. Причина — в исходнике `kwin-forceblur-6.7/src/blur.cpp`:
   размытие РАМКИ (`frame` region, в отличие от `content` region) включается
   только если `decorationSupportsBlurBehind(w)` истинно, а это требует, чтобы
   активный движок декорации сам вызвал
   `KDecoration3::Decoration::setBlurRegion()`. Проверены оба движка Aurorae,
   установленных в системе:
   - `org.kde.kwin.aurorae.v2` (активный по умолчанию) — в бинарнике нет
     логики расчёта блюр-региона для рамки вообще;
   - `org.kde.kwin.aurorae` (старый) — в бинарнике есть функция `updateBlur`,
     но живой тест (тот же метод сравнения пикселей) всё равно показал
     резкую, а не размытую рамку.

   Значит ни один из двух движков Aurorae, доступных в системе, реально не
   регистрирует блюр-регион рамки — это системное ограничение, не специфика
   темы MacTahoe или WhiteSur.

## Решение

Раз декорация не регистрирует свой блюр-регион сама — эффект считает его
самостоятельно, в обход Aurorae, для окон из форс-списка классов.

В `source/kwin-forceblur-6.7/src/blur.{h,cpp}` добавлен метод
`forceDecorationBlurRegion()`:

```cpp
RegionF BlurEffect::forceDecorationBlurRegion(const EffectWindow *w) const
{
    if (!w->decoration()) {
        return RegionF();
    }
    return RegionF(w->decoration()->rect()) - w->contentsRect();
}
```

и в `updateBlurRegion()`, рядом с уже существующим форс-блюром для `content`,
добавлена аналогичная ветка для `frame`:

```cpp
const bool forceBlurWindow = shouldForceBlur(w);

if (!content.has_value() && forceBlurWindow) {
    content = RegionF();
}

if (!frame.has_value() && forceBlurWindow) {
    frame = forceDecorationBlurRegion(w);
}
```

`shouldForceBlur(w)` — уже существующая в апстримном форс-блюре проверка
класса окна (`[Effect-blur] WindowClasses`, без учёта регистра, по вхождению),
расширенная в этом проекте (2026-07-28) поддержкой значения `*` — если хотя
бы один элемент списка (после `trim()`) равен `*`, форс-блюр включается для
ЛЮБОГО окна (кроме десктопа/доков, отфильтрованных в начале функции), минуя
сравнение класса вообще:

```cpp
for (const QString &cls : m_windowClasses) {
    const QString needle = cls.trimmed();
    if (needle == QLatin1String("*")) {
        return true; // force blur for every window
    }
    if (!needle.isEmpty() && windowClass.contains(needle, Qt::CaseInsensitive)) {
        return true;
    }
}
```

Настоящая правка — эти ~10 строк плюс wildcard-проверка; остальной файл
идентичен исходнику из `../MacOS/`.

## Конфигурация

```ini
[Plugins]
blurEnabled=false
forceblurEnabled=true

[Effect-blur]
BlurStrength=15
NoiseStrength=0
WindowClasses=*
```

`WindowClasses=*` (значение по умолчанию `tools/install-kwin-forceblur.sh`
с 2026-07-28) форсирует блюр рамки/контента для ВСЕХ окон в системе, не
только Dolphin/Alacritty — так рамка любого окна (System Settings, Kate,
Firefox и т.д.) получает тот же полупрозрачный вид, что и у Dolphin. Чтобы
вернуть точечный список конкретных приложений вместо `*`, задать
`FORCEBLUR_CLASSES` явно при запуске скрипта, например
`FORCEBLUR_CLASSES=dolphin,alacritty tools/install-kwin-forceblur.sh` —
значения класса перечисляются через запятую.

## Как собрать/установить

```bash
tools/install-kwin-forceblur.sh
tools/check-kwin-forceblur.sh
```

Первый скрипт: собирает `forceblur.so` из `source/kwin-forceblur-6.7`,
ставит его в `$(qtpaths6 --query QT_INSTALL_PLUGINS)/kwin/effects/plugins/`
(системный путь — тот же файл использует и проект `../MacOS/`, если там тоже
включён форс-блюр; последняя пересборка побеждает), выгружает штатный `blur`
и загружает `forceblur` через D-Bus, применяет `kwriteconfig6`.

## Обслуживание

Тот же плагин, что и в `../MacOS/` — то же требование к пересборке. В этом
проекте уже дважды (2026-07-12, 2026-07-20) даже patch-обновление
`kwin-*`/KF6 ломало приватный ABI, от которого зависит `forceblur.so`
(симптом: файл и конфиг на месте, но
`qdbus6 org.kde.KWin /Effects org.kde.kwin.Effects.isEffectLoaded forceblur`
возвращает `false`). Правило то же: после **любого** обновления пакетов
`kwin-*`/KF6 — `tools/check-kwin-forceblur.sh`, при `loaded=false` —
`tools/install-kwin-forceblur.sh` (пересборка без правки кода).

## Важно: unloadEffect/loadEffect НЕ гарантирует перечитывание .so с диска (2026-07-28)

Обнаружено экспериментально при отладке бага со скруглением углов (см. ниже):
`qdbus6 org.kde.KWin /Effects org.kde.kwin.Effects.unloadEffect forceblur` +
`loadEffect forceblur` (ровно то, что делает `install-kwin-forceblur.sh`)
**не обязательно** заставляет `kwin_wayland` реально перечитать файл `.so` с
диска — судя по всему, процесс может держать уже загруженный экземпляр
плагина в памяти и просто переключать его логическое состояние вкл/выкл, а
не делать честные `dlclose`+`dlopen`. Проверено так: пересобрал плагин с
заведомо новым отладочным `qCWarning`, переустановил (md5 файла на диске
совпадает со свежей сборкой), выполнил unload+load+reconfigure — но новая
строка лога ни разу не появилась в `journalctl`, хотя старые логи из ЭТОГО
ЖЕ файла продолжали писаться (то есть работал старый, первый загруженный
экземпляр).

**Следствие:** после первой закачки `forceblur.so` в рамках одной livesession
(один вход в Wayland-сессию) последующие пересборки/переустановки **не
гарантированно** подхватываются, даже если `tools/install-kwin-forceblur.sh`
отработал без ошибок и `isEffectLoaded forceblur` вернул `true`. Единственный
надёжный способ подхватить пересобранный `.so` — **выйти из сессии и зайти
заново** (или перезагрузка); на Wayland `kwin_wayland` — это сам композитор
сессии, штатного «мягкого» способа перезапустить только его без завершения
сессии нет. Если после пересборки нужно ГАРАНТИРОВАННО проверить эффект
вживую — закладывать перелогин в план проверки, не полагаться на
unload/load через D-Bus как на доказательство.

## Баг: тень в углу не скруглена (обнаружен 2026-07-28, статус: исправлено, подтверждено вживую)

После фикса острых углов от блюра (см. выше) пользователь заметил на
скриншоте, что угол всё ещё выглядит неровным. Строгая проверка (скриншот
окна + отдельный скриншот тех же экранных координат без окна, попиксельное
сравнение) показала: между реальной геометрической границей окна и видимой
скруглённой кромкой titlebar есть тёмная полоса (~50-65 единиц RGB темнее
ожидаемого), с резкой границей ровно на границе окна.

Источник — не блюр, а сама SVG-тема: `decoration.svg`, группы
`decoration-topleft`/`decoration-inactive-topleft`, элементы `path1019`
(активное состояние) и `rect6520-3-2-6` (неактивное) — это радиальный
градиент-тень (`shadow_active`/`shadow_inactive`, чёрный с затуханием
прозрачности), но контур-маска этой тени описан как обычный прямоугольник
со скруглённой ВНУТРЕННЕЙ выемкой (примыкающей к видимой белой заливке) —
внешний контур прямой, поэтому тень обрывается резко на границе окна вместо
плавного затухания.

**Исправление применено** (в `~/.local/share/aurorae/themes/MacTahoe-Light/decoration.svg`
и синхронизировано в `source/MacTahoe-kde/aurorae/MacTahoe-Light/decoration.svg`):
внешний угол обеих фигур (в локальных координатах `(40,65)` для `path1019`,
`(400,59)` для `rect6520-3-2-6`) заменён квадратичной кривой Безье (`Q`) с
радиусом скругления 24 (тот же, что и у видимой кривой), используя исходный
острый угол как контрольную точку — стандартный приём построения фаски.

**Статус проверки:** подтверждено вживую после перелогина/перезагрузки
сессии (2026-07-28) — пользователь визуально проверил Dolphin, скруглённый
угол без резкой тёмной полосы, блюр отображается как нужно. До перелогина
множественные попытки проверки давали одинаковый результат независимо от
правки — причина в кэшировании (см. раздел выше про `.so` и собственное
кэширование Aurorae отрисованных SVG-элементов на уровне процесса
`kwin_wayland`, не сбрасываемое надёжно через `rm -rf ~/.cache/ksvg-elements`
+ переключение темы туда-обратно, пока хоть один процесс сессии — например,
Alacritty — непрерывно использует тему MacTahoe-Light). Перелогин оказался
единственным надёжным способом подтвердить фикс.

## Как проверить, что рамка реально размыта (а не просто прозрачна)

Резкая альфа-прозрачность и настоящий блюр визуально почти неотличимы на
плоских участках обоев — проверять только на границе с деталями (силуэт
горы, облако):

```bash
dolphin ~/Documents/Theme/Tahoe &
sleep 2
kdotool windowmove "$(kdotool search --name Dolphin | head -1)" 1600 830
spectacle -b -n -o /tmp/check.png
```

Сравнить пиксели заголовка над контрастной деталью обоев с пикселями тех же
X-координат чуть выше окна (необработанные обои). Если значения совпадают —
это резкая прозрачность (блюр не работает). Если заголовок заметно светлее и
сглаженнее детали позади — блюр реально работает.

### Статус проверки: подтверждено (2026-07-28)

Визуальное сравнение пикселей ненадёжно на глаз (резкая alpha-прозрачность и
слабый блюр почти неотличимы), поэтому проверено количественно: два
скриншота одной и той же области экрана (силуэт горы на обоях, тайтлбар
Dolphin придвинут прямо на него) — один с окном, один без (`spectacle`),
затем в чистой от иконок/текста полосе тайтлбара (~200×30 px) сравнены
стандартное отклонение яркости фактического кадра и трёх прогнозов:

- без блюра (0.75×белый + 0.25×resкие обои по тем же координатам): std≈8;
- фактический тайтлбар: std≈1–2;
- прогноз совпадает с фактическим только при gaussian-блюре обоев с радиусом
  ~80–120 px перед тем же alpha-blend.

Резкая прозрачность (radius=0) даёт разницу в 4-5 раз по std — исключена.
Совпадение достигается только при сильном блюре — `forceDecorationBlurRegion()`
действительно применяет блюр к рамке, а не просто рисует alpha-прозрачную
заливку. Метод воспроизводим: скрипт использовался разово из шелла, не
сохранён в `tools/` (не нужен для регулярного обслуживания — визуальной
проверки `tools/check-kwin-forceblur.sh` для loaded=true достаточно на
практике; численный тест — на случай, если понадобится доказать реальность
блюра ещё раз).

## Баг и фикс: острые уголки поверх скруглённой рамки (2026-07-28)

**Симптом** (обнаружен пользователем по скриншоту): в обоих верхних углах
заголовка Dolphin торчали маленькие тёмные квадратные наросты за пределами
скруглённого силуэта декорации — видно на границе с обоями.

**Причина:** `forceDecorationBlurRegion()` строила регион блюра как плоский
прямоугольник (`decoration()->rect() - contentsRect()`), не зная о скруглении
углов окна вообще. Скругление углов в этой теме — не часть Aurorae/SVG, а
отдельный сторонний KWin-скрипт «Rounded corners» (см. `README.md` проекта:
верхний/нижний радиус угла — `24`), который клипает уже готовую отрисовку
самого окна (декорация+контент), но **не** более ранний проход, которым Blur
рисует размытую подложку под окном. Из-за этого блюр-подложка рисовалась по
всему прямоугольнику декорации, включая квадратные уголки за пределами
кривой, а сам скрипт клипал только окно — и наросты оставались видны.

**Исправление:** в `source/kwin-forceblur-6.7/src/blur.cpp` добавлена
`cutRoundedCorner()` — аппроксимация четверти окружности построчными
прямоугольниками (радиус `kForcedCornerRadius = 24`, должен совпадать со
значением скрипта «Rounded corners»; `RegionF` хранит только
axis-aligned-прямоугольники, точной кривой там нет). `forceDecorationBlurRegion()`
теперь вычитает такой вырез из всех четырёх углов `decoration()->rect()`
(в этой теме реально используются только два верхних — рамка без боковых/
нижней границы). Подтверждено визуально (`spectacle`, до/после) на тех же
координатах экрана: наросты исчезли, кривая гладкая с обеих сторон.

**Если радиус в системе меняют** (правка скрипта «Rounded corners» на другое
значение) — `kForcedCornerRadius` в `blur.cpp` нужно поправить вручную и
пересобрать (`tools/install-kwin-forceblur.sh`), иначе баг вернётся в
уменьшенном/увеличенном виде (несовпадение радиусов даёт неполный вырез или
избыточный вырез внутрь кривой).
